# Product Requirements Document (PRD)

# Telegram E-Commerce Shop Bot

**Version:** 2.0

**Platform:** Telegram

**Backend:** Python / aiogram

**Database:** PostgreSQL

**Supported Languages:** Russian, English, German, Ukrainian

---

# 1. Project Overview

The project is a Telegram-based e-commerce shop for selling vape e-liquids.

The bot provides:

- multilingual user interface;
- product catalog;
- hierarchical product navigation;
- shopping cart;
- checkout;
- order management;
- administrator panel;
- manager notifications;
- customer order status notifications;
- broadcast messaging;
- customer review group integration;
- sales and product statistics.

The bot must be fast, intuitive, mobile-first and easy to maintain.

The entire administration workflow must be available through Telegram without requiring a separate web administration panel.

17. Group Chat Isolation

The bot must NOT process user or administrator interactions from group chats.

The bot should only process interactive commands and callbacks in:

private chats with users;
private chats with administrators.

The bot must ignore interactions originating from groups and supergroups.

Requirements:

no command processing in groups;
no FSM conversations in groups;
no admin commands in groups;
no inline interaction flows in groups;
no Reply Keyboard sent to groups;
no catalog buttons sent to groups;
no checkout interaction in groups;
no broadcast interaction in groups.

The manager group should only receive outgoing order notifications.

The bot must never accidentally respond to messages such as:

/start
/admin
/orders
/stats

when they are sent inside the manager group.

Group messages must be ignored silently.

This restriction must be enforced at the middleware/router/filter level rather than implemented separately in every handler.

# 33. Critical Production Issue — Catalog Disappears After Bot Updates

There is currently a reported production issue:

> "Every time the bot is updated, the assortment disappears."

Important clarification:

The catalog does NOT appear to disappear when an administrator creates, edits or updates products.

The reported issue occurs after the bot/application itself is updated, restarted, redeployed or otherwise replaced.

The exact root cause is currently unknown.

This must be treated as a critical production issue and investigated before or alongside implementation of the new catalog functionality.

The developer must NOT assume that the database is necessarily the root cause.

The investigation must cover the complete application update lifecycle:

- application restart;
- Docker container restart;
- Docker Compose recreation;
- image rebuild;
- container replacement;
- deployment scripts;
- PostgreSQL container lifecycle;
- PostgreSQL persistent volumes;
- database connection configuration;
- DATABASE_URL;
- environment variables;
- Alembic migrations;
- startup initialization;
- seed scripts;
- database initialization scripts;
- automatic schema creation;
- destructive migrations;
- application startup tasks;
- deployment scripts;
- CI/CD configuration;
- server filesystem;
- Docker Compose volume configuration;
- container filesystem;
- database hostnames;
- database names;
- database users;
- possible connections to different databases/environments.

The objective is to determine exactly why catalog data disappears after an application update.

# 35. Update / Deployment Persistence Requirements

Updating the bot must NEVER cause existing production data to disappear.

The following operation must preserve all persistent data:

- application restart;
- bot process restart;
- Docker container restart;
- Docker Compose restart;
- Docker Compose container recreation;
- Docker image rebuild;
- application image replacement;
- normal application redeployment;
- non-destructive Alembic migration.

Existing data must remain intact:

- users;
- languages;
- selected cities;
- categories;
- subcategories;
- products;
- carts;
- orders;
- order history.

Updating application code must be independent from the lifecycle of persistent PostgreSQL storage.

Production deployment must NOT remove the PostgreSQL volume.

The documented deployment procedure must explicitly distinguish:

Application containers
from
Persistent database storage.

# 36. Safe Deployment Requirements

The production deployment process must follow a safe update model.

Conceptually:

```text
Existing PostgreSQL
        ↓
Persistent volume
        ↓
New application image
        ↓
Database migration
        ↓
Application restart
        ↓
Existing data remains available

The deployment process must NOT perform operations equivalent to:

docker compose down -v

or any other operation that removes the PostgreSQL volume, unless explicitly intended for a complete destructive environment reset.

Production deployment must not:

remove database volumes;
recreate the database unnecessarily;
run destructive initialization;
reset tables;
delete catalog data;
automatically seed production data;
overwrite existing products.

If migrations are required, they must be executed explicitly and safely.

The deployment documentation must clearly distinguish:

Safe operations

Operations that preserve production data.

Destructive operations

Operations that can delete production data and must NEVER be used during normal production updates.
